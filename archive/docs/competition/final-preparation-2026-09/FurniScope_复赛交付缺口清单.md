# FurniScope 复赛交付缺口清单

更新日期：2026-09-10

## 结论

当前工程已经具备较完整的产品设计、FastAPI/LangGraph/PostgreSQL 技术底座、
销量预测模块和可运行 UI，但距离复赛模板要求的“可演示、可理解、可证明业务价值”
仍缺一套收口后的提交证据包。最优先的不是继续扩功能，而是把一条核心业务链路跑通、
录制并量化证明。

## 模板要求与当前缺口

| 模板项 | 当前基础 | 仍需完成 | 优先级 |
|---|---|---|---|
| 团队与参赛信息 | 仓库未见最终填写版 | 团队名、联系人、全体成员、参赛场景、方案名、一句话定义 | P0 |
| 目标用户与痛点 | PRD、README 已有较完整描述 | 压缩成评委可在 1 分钟读懂的 2–3 个痛点，并补访谈/调研证据 | P0 |
| 商业价值 | 有定性价值主张 | 给出可核验基线、目标值、测量方法；避免无依据写“节省 50%” | P0 |
| 市场前景与落地 | 有产品愿景 | TAM/SAM/SOM、首批客户、收费方式、推广路径和合规数据来源 | P1 |
| 核心功能与使用说明 | UI、README、API 文档较全 | 只保留一条主 Demo 链路，补 5–8 张真实运行截图和异常说明 | P0 |
| 系统架构与模型说明 | 架构文档较强 | 改成赛事 Token Plan 实际模型、用途、调用链和审计截图 | P0 |
| 阶段成果 | 代码与测试基础较强 | 明确“已完成 / 演示数据 / 未完成”，不能把原型写成生产能力 | P0 |
| Demo/体验地址 | 本地可运行 | 部署稳定线上地址、准备测试账号、做赛前冷启动验证 | P0 |
| 演示视频 | 未见最终视频 | 3–5 分钟：痛点 20 秒、核心链路 3 分钟、价值与架构 1 分钟 | P0 |
| GitCode 仓库 | 当前 README 指向 GitHub | 决定是否迁移 GitCode；私有仓需授权 `air__Heaven` | P1 |
| 最终 PDF | 只有空白 Word 模板 | 完成内容、转 PDF，并按“团队名_方案名称_复赛作品.pdf”命名 | P0 |

## 目前最值得警惕的表述风险

1. 当前分析 Worker 默认仍是合成数据演示，不能声称已完成真实市场洞察闭环。
2. 前端有大量静态示例内容；演示时必须区分真实 API 返回与视觉原型数据。
3. 销量预测模型已集成，但训练数据代表性、留出集指标、数据泄漏检查和业务基线对比
   需要单独给出，否则 MAPE 等数字不足以证明泛化能力。
4. `api.md` 含赛事专属 API Key。文件已加入本地忽略规则，但密钥若曾发送到远程仓库、
   聊天群或日志，应立即轮换。
5. 模板中的模型标识示例带有 `qwen/` 前缀，而赛事说明给出的实际请求值为
   `qwen3.7-plus`；提交材料应记录真实请求参数，避免照抄示例。

## 建议的唯一主 Demo 链路

1. 选择家具 SKU 和站点，运行销量预测。
2. 展示预测区间、安全库存和建议生产量。
3. 创建市场分析任务，展示五阶段执行与模型调用审计。
4. Token Plan 生成带“演示数据限制”的结构化报告。
5. 打开决策报告，说明证据、置信度、制造建议和待验证项。

## 提交前验收门槛

- 从全新环境按 README 启动成功；核心演示连续运行 3 次无阻塞。
- 视频中出现的每个按钮都有真实响应，或明确标注为原型。
- 提交 PDF、视频链接、Demo 地址、测试账号、仓库地址全部可访问。
- API Key 不出现在仓库、浏览器包、截图、视频、日志和 PDF 中。
- 至少展示一次真实 Token Plan 调用记录，并展示模型名、Token、耗时和 Schema 状态。
- 所有业务提升数字均附基线、样本和测量口径。
