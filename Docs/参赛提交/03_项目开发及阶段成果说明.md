# 三、项目开发及阶段成果说明

> 项目名称：FurniScope 跨境家具超级 AI 员工  
> 更新日期：2026 年 9 月 14 日  
> 当前阶段：赛事演示版完成，进入真实数据接入与试点验证阶段

## 3.1 开发过程

FurniScope 采用“业务调研—需求建模—技术设计—核心链路开发—工程化验证—持续迭代”的方式推进。项目首先围绕跨境家具企业在市场调研、竞品分析、评论洞察、销量预测和生产决策中的实际问题完成需求拆解，明确由企业用户直接使用一个 AI 工作台完成从产品资料输入到决策报告输出的完整闭环。

在产品与技术设计阶段，团队先后完成 PRD/SRS、产品数据字典、PostgreSQL 数据库设计、RESTful API 契约、LangGraph Agent 工作流、页面交互原型和测试用例设计，并通过版本化文档约束前端、后端、数据库和 Agent 的实现范围。系统采用 React 19 + Vite 构建前端，FastAPI 提供业务接口，PostgreSQL 保存租户业务数据和审计记录，Redis Streams 承载异步任务，LangGraph 编排产品理解、市场研究、机会评估、建议生成和报告输出流程，XGBoost 销量预测引擎负责需求预测与生产建议计算。

在核心开发阶段，项目优先贯通“产品建档—市场数据接入—销量预测—市场分析—证据审计—决策报告”主链路，随后补充认证与租户隔离、任务幂等、失败重试、人工确认、安全恢复、监控告警和数据库备份等工程能力。近期迭代进一步实现了 Amazon 商品页、Amazon 评论页和站外评论页的主动采集，打通基于 `schedule_minutes` 的 Worker 定时扫描，并接入钉钉、Slack、通用 Webhook、邮件网关和短信网关通知。

## 3.2 目前已完成的功能

### 1. 产品与企业能力管理

- 支持家具产品的单条创建、批量导入和多文件资料解析。
- 支持 PDF、扫描件、Excel 和图片文字识别，并生成版本化产品画像。
- 支持材料、尺寸、结构、风格、MOQ、成本和企业制造能力等信息管理。
- 对字段来源、置信度和人工确认状态进行记录，避免未经验证的信息直接进入决策链路。

### 2. 市场数据与实时舆情采集

- 支持 CSV、JSON、XLSX 市场数据导入、清洗、质量统计和租户级复用。
- 支持授权 JSON API、RSS/Atom、事件推送等数据接入方式。
- 已实现 Amazon 商品页、Amazon 评论页和通用站外评论页主动采集。
- 网页采集优先读取 JSON-LD 结构化数据，并为 Amazon 商品标题、价格、评分、评论数、图片、卖点和评论正文提供 DOM 回退解析。
- 采集结果自动写入竞品快照和舆情事件表；绑定市场数据集后，还会增量同步至 `market_listings` 和 `reviews`，供 AI 工作流直接复用。
- 采集源保留授权依据、市场、平台、品类、执行状态、最近采集时间和错误摘要，便于追溯。
- 市场洞察首页已重构为“导入数据—自动清洗—用于 AI 分析”的三步引导，统一展示数据集质量、竞品与评论规模，并提供详情溯源和高级动态监控入口。

### 3. 自动调度与异步任务

- Redis Streams Worker 已承载分析、预测、数据导入、产品解析和信号采集任务。
- Worker 启动时立即扫描到期源，运行期间每 30 秒执行一次维护循环。
- 系统根据每个来源的 `schedule_minutes`、`last_fetched_at` 和启停状态自动判断是否到期。
- 到期任务采用状态抢占和任务 ID 去重，避免多个 Worker 重复采集。
- 支持消费组租约、并发控制、失败重试、超时、死信隔离和进程重启恢复。
- 保留手动“立即拉取”能力，便于调试和临时刷新。

### 4. 竞品跟踪、政策预警与外部通知

- 支持 ASIN/商品编号监控、价格曲线、Listing 版本快照、促销变化和新品节奏分析。
- 支持价格、标题、图片、卖点和促销变化检测，并生成可读预警。
- 支持官方政策 RSS/JSON 源、关键词匹配、风险分级和已读状态管理。
- 支持钉钉、Slack、通用 Webhook、邮件网关和短信网关五类通知渠道。
- 新增竞品或政策预警时自动生成待投递事件，Worker 周期性发送并记录投递状态、尝试次数、错误原因和完成时间。
- 前端已提供采集源、调度周期、通知渠道、测试消息和投递记录的配置入口。

### 5. AI 市场分析与决策报告

- LangGraph 已实现产品理解、数据质量检查、竞品筛选、评论分析、需求聚类、市场指标、机会评分、产品建议、证据审计和报告生成流程。
- 支持五阶段任务进度、节点幂等、并行处理、失败降级、Checkpoint、Outbox 和 `user_confirmation` 人工确认。
- 已接入赛事 Token Plan 兼容网关，支持结构化输出、模型调用审计、Token、耗时、重试和 Schema 状态记录。
- 报告可下钻查看竞品、评论原文、需求簇、机会评分、制造建议、风险和证据索引。

### 6. 销量预测与生产建议

- 已集成 Sales Forecast V4/XGBoost 预测引擎和模型资产。
- 支持按 SKU、站点、日/周周期进行预测，并输出预测区间、安全库存和建议生产量。
- 支持企业追加订单与库存数据、触发租户模型训练、查看历史记录及导出结果。
- 已完成 1204 个 SKU 的目录覆盖审计，其中 401 个具备留出标签的 SKU 完成 8 周回测；其余 803 个无观测标签的 SKU 不虚构精度结果。

### 7. 工程化与安全能力

- 已完成 RS256 JWT、Refresh Token 轮换与重放检测、用户/管理员权限边界和租户隔离。
- 已实现持久化幂等、统一响应结构、业务错误码、请求 ID、日志脱敏和审计日志。
- 已提供 Docker Compose、Backend/Frontend/Worker 镜像、健康检查和 GitHub Actions 配置。
- 已接入 Prometheus、Grafana、告警规则、PostgreSQL 每日备份及恢复脚本。

## 3.4 遇到的挑战及解决方案

### 挑战一：不同网站页面结构差异大

Amazon 商品页、评论页和站外评论页的 HTML 结构并不统一，单纯依赖固定 CSS 选择器容易因页面更新失效。

解决方案：建立统一网页信号解析层，优先使用 Schema.org JSON-LD 提取商品和评论事实；针对 Amazon 常见 `id`、`class` 和 `data-hook` 增加 DOM 回退策略。解析输出统一转换为现有 `listings/reviews` 数据结构，使 API、网页采集和事件推送共享同一入库、去重、情感判断和竞品差异检测逻辑。

### 挑战二：定时字段已保存但任务没有真正执行

早期版本已保存 `schedule_minutes`，也实现了到期查询方法，但 Worker 的周期循环只执行故障恢复，没有调用到期源入队和通知投递，导致系统表面上可配置、运行时仍依赖手工操作。

解决方案：将到期源扫描和通知投递纳入 Worker 启动流程与 30 秒维护循环；通过数据库状态抢占、`last_queued_at`、分钟级任务 ID 和 Redis 去重控制并发，失败入队时回写错误状态，陈旧的 `queued` 状态可由恢复流程自动释放。

### 挑战三：采集、预警和外部通知之间缺少闭环

竞品变化和政策预警虽然能够入库，但缺少统一的外发事件模型，无法确认消息是否真正送达。

解决方案：新增租户级通知渠道和通知事件表。业务预警先事务性写入待投递事件，再由 Worker 异步发送；不同渠道使用相应消息格式，钉钉支持环境变量签名，所有渠道统一记录成功、失败、重试次数和错误摘要。

### 挑战四：数据库测试环境缺失导致用例跳过

仅收集到测试但没有设置 `FURNISCOPE_TEST_DATABASE_URL`，无法证明 SQL、租户隔离、队列状态和事务行为真实可用。

解决方案：创建独立 PostgreSQL 16 测试库，从完整 V3 DDL 初始化数据库，并显式设置 PostgreSQL 与 Redis 测试连接运行相关集成测试。新增用例覆盖主动网页解析、评论入库、到期调度、通知排队和投递状态更新，不再使用 skipped 结果替代验收。

### 挑战五：现有运行库与新增迁移版本不一致

当前运行库已有核心业务表，但尚未执行信号采集与通知迁移，Worker 在恢复阶段访问缺失表时会退出。

解决方案：按依赖顺序执行 `v3_7_authorized_market_signals.sql`、`v3_8_alert_notifications.sql` 和 `v3_9_active_web_collection.sql`，保留原有业务数据后重启 Backend 与 Worker，并确认服务恢复运行。

## 3.5 后续迭代计划

1. **采集适配增强**：增加页面模板版本识别、分页采集、增量游标、失败页面留样和解析成功率监控，持续适配 Amazon 及重点站外评论网站的页面变化。
2. **浏览器采集能力**：针对必须执行 JavaScript 才能渲染的页面增加独立浏览器采集 Worker，并与现有 Redis 队列、限流和审计体系复用。
3. **通知可靠性提升**：增加指数退避、渠道级限流、投递回执、告警合并、静默时段和升级策略，补充真实钉钉、Slack、邮件及短信账号的端到端验收。
4. **全量测试收口**：修复现有 4 项模型路由/测试契约失败，统一测试环境隔离规则，使全量后端测试在 CI 中连接真实 PostgreSQL 和 Redis 且达到 0 failed、0 skipped。
5. **真实数据验证**：使用企业授权的 Amazon 与站外评论目标连续运行采集，统计成功率、更新延迟、重复率和字段完整度，并形成可审计验收报告。
6. **模型效果深化**：补齐 SKU 在售状态和品类主数据，从原始订单按因果时间窗重建训练集，完成多折滚动回测、冷启动评估和业务基线对比。
7. **试点与运营闭环**：邀请目标家具企业试用，围绕分析周期、证据覆盖率、建议采纳率、预测偏差、缺货率和库存周转建立量化 KPI。

## 3.6 阶段结论

FurniScope 已从 UI 原型和单点算法发展为具备真实前后端、数据库、异步 Worker、Agent 工作流、销量预测、主动市场采集、自动调度和外部通知能力的可运行系统。当前版本可以完成从产品与市场数据输入，到销量预测、竞品与舆情分析、机会评估、制造建议和决策报告输出的完整演示闭环。下一阶段重点将从“功能贯通”转向“真实目标连续采集、全量测试清零、模型效果量化和企业试点验证”。
