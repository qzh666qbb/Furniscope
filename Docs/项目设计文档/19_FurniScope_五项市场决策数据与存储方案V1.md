> 状态：已实现并完成本地工程验证  
> 日期：2026-10-07  
> 适用范围：决策中心的智能选品、竞品动态追踪、评论深挖、智能定价、跨境合规预警  
> 权威上位文档：`15_FurniScope_企业决策与数据闭环总体设计V1.md`

## 1. 目标与边界

本方案解决五项能力缺少可消费数据的问题，并建立统一的版本、来源、规则、校验和、
权限与恢复机制。业务结果继续写入现有权威表，治理层只记录批次和逐记录血缘，不复制
完整评论正文或商品大字段。

数据分为四类：

| 分类 | 定义 | 可直接作为外部事实 |
|---|---|---:|
| `authorized_source_record` | 企业授权数据集中的原始记录或当前快照 | 仅在授权范围和来源限制内 |
| `derived_result` | 可由输入记录和固定规则重新计算的结果 | 必须同时展示规则、置信度和数据边界 |
| `planning_assumption` | 用于经营推演的参数 | 否，执行前必须由企业确认 |
| `official_source_registry` | 官方公开政策入口的连接配置 | 入口本身可以；公告内容须在采集后单独入库 |

硬边界：

1. 不扩写不存在的历史价格、评论增长或政策事件。
2. 评论观点必须保留原文连续区间和内容哈希。
3. 经营规划值不得标记为企业已确认事实。
4. 官方源未采集到公告时，预警数量保持为零。
5. 业务表保存可消费结果，治理表保存来源与计算依据，两者不能互相替代。

## 3. 数据结构设计

### 3.1 权威业务表

| 能力 | 权威表 | 说明 |
|---|---|---|
| 智能选品 | `analysis_tasks`、`market_opportunities`、`market_metrics`、`price_bands` | 保存任务、机会项和价格统计 |
| 竞品动态追踪 | `competitor_watch_targets`、`competitor_listing_snapshots`、`competitor_change_alerts` | 保存观察对象、快照和变化事件 |
| 评论深挖 | `reviews`、`review_aspects`、`insight_clusters`、`cluster_members` | 保留原文、证据观点和聚类 |
| 智能定价 | `market_listings`、`enterprise_profiles.constraints` | 市场价格与企业约束分开保存 |
| 跨境合规预警 | `policy_sources`、`policy_alerts` | 官方入口与公告分开保存 |

前端现有`MarketIntelligenceService`直接读取这些表，无需增加第二套消费逻辑。

### 3.2 治理表

#### `market_intelligence_batches`

| 字段组 | 字段 | 用途 |
|---|---|---|
| 身份 | `batch_uuid/tenant_id/package_id/package_version` | 租户内唯一定位数据包 |
| 范围 | `dataset_id/product_id/scope_snapshot` | 冻结市场、品类、数量和来源边界 |
| 完整性 | `package_sha256/schema_version` | 检测未升版本的内容变化 |
| 来源 | `source_summary` | 保存授权引用、来源类型和输入摘要 |
| 生命周期 | `staged/active/superseded/revoked/failed` | 控制生效、替换与撤销 |
| 审计 | `imported_by/imported_at/activated_at/*_at` | 保存操作者和关键时间 |

同一企业、同一`package_id`最多一个`active`批次。批次身份字段不可修改，状态只能按
`staged -> active|failed -> superseded|revoked`允许的方向迁移。

#### `market_intelligence_lineage`

| 字段组 | 字段 | 用途 |
|---|---|---|
| 归属 | `tenant_id/batch_id/capability_code` | 定位企业、批次和能力 |
| 目标 | `target_table/target_record_id/natural_key` | 关联业务表记录 |
| 来源 | `source_class/source_locator` | 保存来源标识、记录ID和证据区间 |
| 规则 | `derivation_rule/rule_version` | 支持复算和版本比较 |
| 完整性 | `input_sha256/payload_sha256` | 校验输入和输出 |
| 质量 | `confidence/observed_at/valid_from/valid_until` | 保存可信度和时间语义 |

血缘表只允许插入，更新和删除由触发器拒绝。`source_locator`禁止存令牌、凭据和完整评论
正文。

## 4. 存储介质选择

| 数据 | 介质 | 原因 |
|---|---|---|
| 结构化业务结果 | PostgreSQL 16 | 事务、约束、复合外键、RLS、索引和一致性查询 |
| 批次与血缘 | PostgreSQL 16 | 必须与业务写入处于同一事务 |
| 原始上传文件与大附件 | S3兼容对象存储 | 降低数据库膨胀，使用租户前缀、版本和对象锁 |
| 规则包与迁移 | Git版本库 | 代码评审、SHA、版本发布和回滚可追溯 |
| 完整导出 | 受控文件区或对象存储 | 便于离线审核，不作为在线权威源 |
| 短时缓存 | Redis | 只缓存可重建投影，不保存唯一事实 |

PostgreSQL保持唯一业务事实源。JSON文件是可审核输入和导出，不允许由应用绕过数据库直接
当作在线主数据。

## 5. 访问权限控制

### 5.1 数据库边界

1. 两张治理表均启用`ENABLE ROW LEVEL SECURITY`和`FORCE ROW LEVEL SECURITY`。
2. `furniscope_tenant`只能访问`tenant_id=current_tenant_id()`的记录。
3. `furniscope_platform_admin`拥有显式管理策略；应用进程不得使用超级用户或
   `BYPASSRLS`身份。
4. 治理表挂载租户迁移写栅栏，租户处于迁移状态时阻断普通写入。
5. 血缘不可修改；批次只允许受控状态变更；不开放物理删除。

### 5.2 应用权限

| 操作 | 建议权限 | 角色 |
|---|---|---|
| 查看五项能力与血缘摘要 | `analysis.read` | viewer及以上 |
| 重新生成业务结果 | `analysis.execute` | operator、analyst、data_admin、owner |
| 修改数据集或规划参数 | `dataset.write` | data_admin、owner |
| 撤销批次 | `tenant.settings.write` | owner |
| 查看完整审计与恢复记录 | `audit.read` | auditor、owner |

API仍需在服务层检查RBAC，不能因为数据库RLS存在就省略业务权限。

### 5.3 机密性与完整性

- 传输使用TLS，生产存储使用云盘或数据库服务端加密。
- 凭据只进入密钥管理服务或环境变量，不进入规则包、治理表或日志。
- 对象键使用租户前缀；下载使用短时签名地址。
- 数据包、输入集合、逐记录输入和输出都保存SHA-256。
- 评论正文继续留在`reviews.content_original`，治理层只保存记录ID、哈希和区间。

## 6. 可访问性与扩展性

### 6.1 查询路径

在线页面使用`GET /api/v1/market-intelligence/overview`读取五项能力总数和轻量预览；
持续增长的选品机会、竞品动态和评论需求主题分别通过`opportunities`、
`competitor-alerts`和`review-clusters`分页接口读取，并通过对应详情接口下钻。
查询按`tenant_id + dataset_id/task_id`过滤，详情按`tenant_id + record_id`过滤，
治理查询按`tenant_id + batch_id + capability_code`过滤。现有索引覆盖主要路径。

### 6.2 容量增长

| 阶段 | 策略 |
|---|---|
| 单企业十万级业务记录 | 保持普通表，定期`ANALYZE`，使用租户优先复合索引 |
| 千万级快照或观点 | 按时间做范围分区，分区内保留`tenant_id`前导索引 |
| 高频政策与竞品采集 | 采集任务异步化，按来源限流，使用幂等指纹去重 |
| 大型原始文件 | 只在对象存储保存字节，PostgreSQL保存元数据和SHA |
| 历史批次增多 | 在线只读取`active`批次，历史批次保留供审计和复算 |

扩容优先顺序为：优化索引与慢查询、分离采集写入、按时间分区、读副本、租户Cell迁移。
不以复制业务表的方式解决容量问题。

## 7. 长期维护

1. 规则变化必须增加`package_version`和`rule_version`，禁止原地改包。
2. 导入器发现同版本内容SHA变化时立即失败。
3. 新批次激活时旧批次转为`superseded`；旧血缘继续保留。
4. 撤销必须写原因和时间；对应业务记录的处理由受控运维流程完成。
5. 每月检查来源可达性、证书、响应格式、失败率和零结果次数。
6. 每季度复核分类词表、评分权重、规划参数和数据保留策略。
7. 每次结构升级执行fresh、upgrade和重复迁移三类验证。
8. 完整导出不是在线权威源；重建时必须从业务表与血缘表重新导出。

## 8. 备份与恢复

### 8.1 当前工程能力

仓库现有`backup_postgres.sh`每天生成custom-format全库备份，并同时生成：

- dump SHA-256；
- Manifest SHA-256；
- 数据库版本、迁移集合和关键表行数；
- 各租户审计链头。

默认保留14天。`restore_postgres.sh`只允许恢复到显式指定的隔离目标库，恢复前校验两个
SHA和Manifest协议，恢复后复核迁移集合、关键行数与审计链头。单租户导出和恢复使用
`tenant_backup.py`，包内每表与对象均带独立SHA。

### 8.2 生产目标

| 项目 | 目标 |
|---|---|
| WAL归档 | 连续归档，最长15分钟切段 |
| RPO | 不高于15分钟 |
| RTO | 同区域不高于4小时，跨区域不高于12小时 |
| 全量备份 | 每日一次，保留35天 |
| 月度归档 | 每月一次，保留13个月 |
| 跨故障域副本 | 至少一份，独立账号和加密密钥 |
| 恢复演练 | 每月隔离库恢复，每季度租户级恢复与跨区域演练 |

仓库已提供WAL归档参数、复制账号、周期基础备份、校验和按时间点恢复准备脚本，可用于
本地/预发恢复演练。生产上线前仍必须由基础设施提供异地耐久WAL、跨故障域副本并完成
RPO/RTO演练；仓库脚本不能替代托管高可用与跨区域灾备。

### 8.3 恢复验收

恢复后依次检查：

1. `schema_migrations`包含`v3_36_market_intelligence_governance`。
2. 两张治理表均为`FORCE RLS`。
3. `active`批次唯一索引无冲突。
4. 业务表目标记录与血缘`target_record_id`可关联。
5. 数据包SHA、输入SHA和逐记录输出SHA一致。
6. 五项能力API状态和恢复前一致。
7. 跨企业查询返回空集或拒绝响应。
