# 1. 执行摘要

## 1.1 一句话定位

FurniScope 是一款面向中国跨境家具制造企业的 AI 产品决策工具：它将海外竞品、价格、商品表现和用户评论转化为可追溯的需求缺口，再结合工厂的 SKU、材料、工艺、成本、MOQ 和认证能力，输出“值不值得做、适合卖到哪里、应该如何改”的决策建议。

## 1.2 核心业务问题

家具制造企业并不缺产品资料，而是缺少从市场信号到产品动作的转换能力。现有决策链路中存在四个断点：

1. 海外评论、竞品和价格数据量大且分散，人工无法稳定、系统地处理；
2. 消费者的自然语言抱怨无法直接转化为材料、尺寸、结构、包装等工程要求；
3. 通用市场工具可以说明“市场热不热”，但不知道“这家工厂能不能做、做了是否有利润”；
4. 分析结论缺少原始证据、样本量和置信度，不足以支撑打样、开模和备货等高成本决策。

## 1.3 产品价值主张

FurniScope 不替代企业决策者，也不承诺“预测爆款”。它的价值是将原本分散、不可解释的市场信号，转化为可快速验证的产品假设，并显著缩短从“看到市场变化”到“形成打样建议”的时间。

## 1.4 本版本决策

- **选定赛道：**AI 市场洞察。
- **MVP 品类：**沙发，不泛化覆盖所有家具。
- **MVP 市场：**先选定一个国家和一个平台数据集，默认演示为美国 Amazon，但数据可用性需在开发前确认。
- **MVP 核心链路：**产品理解 → 竞品筛选 → 评论洞察 → 需求缺口 → 制造适配 → 机会报告。
- **MVP 产品形态：**Web 端可运行 Demo。
- **明确不做：**自动找客户、自动发邮件、广告投放、完整 Listing 生成和无数据依据的销量预测。

# 2. 项目背景与行业判断

## 2.1 行业现状

跨境电商 AI 已经从单点文案工具进入平台内嵌阶段。Amazon 已支持通过简短描述、图片或网页链接生成商品标题、要点和描述，并提供 Product Opportunity Explorer 分析搜索、购买、评论和价格等信号。Shopify Magic 也已在商店后台提供商品描述、邮件标题、客服回复和媒体生成等能力。

这意味着：

- “帮卖家写 Listing”已是平台基础能力，难以形成参赛差异化；
- “汇总 Amazon 评论”也不足以单独构成创新性；
- 垂直创新机会不在内容生成本身，而在于行业语义理解、企业私有能力匹配和决策证据化。

## 2.2 家具跨境业务特殊性

家具不是低决策、低退货成本的标准品。它具有以下特征：

1. **产品属性复杂。**沙发的座深、座高、海绵密度、面料、框架、模块结构、包装体积和安装方式会共同影响用户体验。
2. **消费语言与工程语言不一致。**“坐久了塌”需要转换为海绵回弹、密度、层结构或支撑设计问题，不是简单情感分析。
3. **价格与履约约束强。**体积、包装、运费、关税、退换成本和 MOQ 都会改变产品的可行价格带。
4. **审美和场景差异明显。**户型、家庭结构、宠物、清洁习惯和本地审美都可能改变对颜色、尺寸和面料的偏好。
5. **错误决策成本高。**产品建议最终可能触发打样、开模、认证、备料和备货，因此系统必须输出证据、风险和待验证项。

## 2.3 市场与竞品格局

| 能力类型 | 典型产品/平台 | 已解决问题 | FurniScope 不应重复的能力 | 可形成的差异 |
|---|---|---|---|---|
| 平台内置商家 AI | Amazon、Shopify 等 | Listing、商品描述、店铺运营辅助 | 泛化文案生成 | 平台外企业数据与制造能力联合分析 |
| 市场机会工具 | Amazon Product Opportunity Explorer 等 | 类目需求、搜索、评论和价格洞察 | 只做 Amazon 市场信号摘要 | 家具需求本体、工厂适配和工程化建议 |
| 销售情报工具 | 通用选品/竞品数据平台 | 排名、价格、销量代理指标 | 再做一个数据看板 | 把外部数据转为企业可执行的产品决策 |
| 通用大模型 | Qwen、DeepSeek 等 | 摘要、分类、推理、报告 | 单次 Prompt 生成报告 | 标准数据模型、确定性计算、证据链和人工复核 |

## 2.4 竞争壁垒假设

FurniScope 的初期壁垒不是基础模型，而是四类可持续积累的业务资产：

- 沙发及后续家具品类的属性、需求和工艺本体；
- “消费者表达 → 产品问题 → 工程动作”的映射规则和专家标注数据；
- 企业历史产品、报价、订单与能力画像；
- 产品建议经打样、上市后的反馈闭环。

# 3. 客户调研结论与需求证据

## 3.1 已获得的初步证据

| 调研发现 | 业务含义 | 对应产品决策 |
|---|---|---|
| 当前出口最多的产品为沙发 | 应以沙发做 MVP，而不是继续假设办公椅为主 | V1 品类收缩为沙发 |
| 高利润产品通常“卖点多、功能多” | 价值不能只看低价，需要识别功能价值与价格空间 | 报告中必须包含功能卖点和利润约束 |
| 低价、易模仿产品竞争最激烈 | 单纯降价不能形成可持续策略 | 增加同质化和差异化空间分析 |
| 新品开发会查看用户评价和 Amazon 销量 | 用户已有分析习惯，但效率和深度不足 | 产品不需要教育“为什么看评论”，而要显示更高质量结果 |
| 出现过审美、价格、功能不匹配导致产品难卖 | 新品决策缺少系统性市场证据 | 输出市场、价格带、功能缺口和审美特征 |
| Amazon 竞品每天分析 | 该任务频率高，具有重复性 | 市场数据导入和重复分析具备使用价值 |
| 企业拥有图片、CAD、参数、报价、订单和邮件 | 具备企业能力画像的基础，但数据质量待核验 | MVP 先使用图片、参数和报价，订单后续接入 |
| AI 需求第一位为市场趋势和新品机会 | 市场洞察比资料生成更接近根因 | 选择 AI 市场洞察赛道 |

## 3.2 尚未验证的关键信息

以下信息在问卷中未填写或标记为不确定，不得作为已知事实写入演示结论：

- 各品类出口占比、收入和毛利率；
- 增长最快的品类；
- Amazon 具体 SKU、销量和站点；
- 企业是否拥有可导出的竞品和 Amazon 数据；
- 历史成功产品案例与失败案例；
- 价格之外的卖点优先级；
- 企业的具体工艺、认证、MOQ、交付周期和包装能力。

## 3.3 问卷中的表面冲突及解释

| 表面冲突 | 产品解释 |
|---|---|
| “最大问题是不知道找谁买”，但客户开发困难中未选“不知道找哪些客户” | 可能分别指“不知道哪类买家有需求”和“已知买家但不理解具体需求”，需二次访谈澄清 |
| 新品开发称未关注竞品，Amazon 又称每天分析竞品 | 可能是 B2B 产品开发与 B2C Amazon 运营两组流程分离，PRD 不将两者混为一个用户旅程 |
| 市场数据是方向决策依据，但市场数据资产又不确定 | 企业可能在人工查看数据，但没有沉淀成可复用数据集 |

# 4. 产品目标、非目标与成功标准

## 4.1 产品目标

### G1：建立统一产品画像

将图片、参数表、PDF 和报价中的分散信息转化为可校验、可追溯的结构化产品画像。

### G2：识别可解释的海外需求缺口

从竞品评论和商品数据中识别采购动机、高频问题、人群和场景，并明确样本范围。

### G3：将需求缺口转化为可执行产品动作

将消费者表达映射到尺寸、材料、结构、包装、成本和验证方法。

### G4：将市场机会与工厂能力联合判断

同时考虑工厂工艺、材料、成本、MOQ、认证和交付约束，避免推荐“市场好但工厂不能做”的方向。

### G5：在复赛中完成稳定、可证明价值的 Demo

用一款真实沙发和一份可复现的市场数据集跑通完整闭环，使评委可以在短时间内看到输入、分析、证据和决策输出。

## 4.2 非目标

V1 不承担以下任务：

- 不保证新品成为爆款；
- 不替代企业进行打样、财务和供应链决策；
- 不自动获取或爬取未授权数据；
- 不自动修改 CAD 或生产图纸；
- 不提供客户名单搜索、邮件触达和 CRM；
- 不提供广告自动投放或自动调价；
- 不在 MVP 中同时覆盖 B2B 获客和 B2C 运营全流程。

## 4.3 北极星指标

**有效产品机会报告数：**被企业产品负责人评定为“存在明确证据、至少一项建议可进入人工评审或打样讨论”的报告数。

## 4.4 MVP 成功标准

| 类别 | 指标 | MVP 目标 | 验证方法 |
|---|---|---:|---|
| 业务价值 | 企业专家对报告可用性评分 | ≥4/5 | 客户产品、外贸或 Amazon 运营人员盲评 |
| 需求准确性 | 家具需求标签 Macro-F1 | 目标≥0.85 | 人工标注测试集 |
| 证据性 | 关键结论证据关联率 | 100% | 抽查所有高优先级结论 |
| 证据正确性 | 证据确实支持结论的比例 | 目标≥95% | 人工审核 |
| 性能 | 1,000 条评论的完整分析时间 | 目标≤5分钟 | 固定数据集压测 |
| 稳定性 | 固定 Demo 链路成功率 | ≥99% | 连续执行 30 次 |
| 交互 | 用户从上传到启动分析的必需操作 | ≤5步 | 可用性测试 |

# 5. 目标用户与角色权限

## 5.1 核心目标客户

### 企业画像

- 中国家具出口制造企业；
- 以 B2B 外贸为主，可同时经营 Amazon 等 B2C 渠道；
- 拥有多个 SKU，具备打样、定制或 OEM/ODM 能力；
- 有产品图片、参数和报价，但市场数据分散；
- 产品决策依赖客户反馈、展会经验和人工竞品分析。

### 不是 V1 优先客户

- 只需要文案或图片生成的小型铺货卖家；
- 不具备产品改造权限的纯分销商；
- 无任何产品资料或市场数据使用权限的个人用户。

## 5.2 用户角色

### R1：企业管理者/老板

- **核心任务：**决定产品方向、目标市场和资源投入。
- **核心关注：**机会是否值得验证、风险是否可控、工厂是否能做。
- **使用频率：**新品立项或月度/季度产品评审。
- **权限：**查看全部报告、配置企业能力、批准或驳回建议。

### R2：产品经理/研发负责人

- **核心任务：**定义产品参数、评估改造可行性、发起打样。
- **核心关注：**需求是否真实、建议能否转化为参数、成本和工艺是否可行。
- **使用频率：**高，贯穿每个新品分析任务。
- **权限：**上传产品、修正产品画像、配置工艺能力、标记建议可行性。

### R3：跨境运营/市场分析人员

- **核心任务：**导入竞品和评论数据，选择目标市场，解读竞争和用户需求。
- **核心关注：**数据范围、竞品是否可比、需求趋势和价格带。
- **使用频率：**高，可按日或按项目使用。
- **权限：**创建分析任务、管理市场数据、查看证据和导出报告。

### R4：外贸业务员

- **核心任务：**理解目标客户可能关注的产品价值。
- **核心关注：**目标人群、使用场景、卖点优先级和反对理由。
- **权限：**只读已发布报告；不查看敏感出厂成本，除非被单独授权。

### R5：系统管理员

- **核心任务：**管理租户、用户、模型配置、数据保留周期和任务异常。
- **权限：**系统配置权；原则上不主动查看企业商业数据。

## 5.3 权限矩阵

| 操作 | 管理者 | 产品/研发 | 市场运营 | 外贸业务 | 系统管理员 |
|---|:---:|:---:|:---:|:---:|:---:|
| 配置企业能力 | ✓ | ✓ | - | - | 受控 |
| 上传/编辑产品 | ✓ | ✓ | ✓ | - | 受控 |
| 导入市场数据 | - | ✓ | ✓ | - | 受控 |

| 查看成本和利润假设 | ✓ | ✓ | 可选 | - | - |
| 查看证据 | ✓ | ✓ | ✓ | ✓ | - |
| 批准建议 | ✓ | 建议权 | - | - | - |

# 6. 核心使用场景

## UC-01：评估一款已有沙发适合哪个目标市场

- **使用者：**产品经理、市场运营。
- **触发时机：**已有产品准备出海，但尚未确定主攻市场和定位。
- **输入：**产品图片、参数、报价、MOQ、候选市场、市场数据集。
- **输出：**产品画像、相似竞品、需求匹配度、价格带、市场风险和证据。
- **业务动作：**选择一个市场进入客户验证或上架准备。

## UC-02：从竞品差评中生成产品改造假设

- **使用者：**产品经理、研发负责人。
- **触发时机：**新品定义、老品改款或客户反馈复盘。
- **输入：**相关竞品评论、当前产品参数、工厂工艺与成本约束。
- **输出：**高频问题、受影响人群、可能根因、参数/材料/结构建议、验证方法。
- **业务动作：**形成打样任务或驳回不可行建议。

## UC-03：比较多个新品候选方向

- **使用者：**企业管理者、产品经理。
- **触发时机：**月度/季度新品立项会。
- **输入：**多个产品画像或需求方向、预估成本、制造能力。
- **输出：**机会分项对比、企业适配度、数据置信度、待验证假设。
- **业务动作：**选出 1—2 个方向进入人工评审。
- **版本：**V1.5，非复赛必做。

## UC-04：复盘一款已上市但转化低的产品

- **使用者：**Amazon 运营、产品经理。
- **触发时机：**产品流量或转化不达预期。
- **输入：**自有商品表现、评论、竞品数据及产品参数。
- **输出：**产品层、价格层与表达层的问题假设，不直接将低转化归因于单一因素。
- **版本：**V2.0。

# 7. 端到端业务流程

## 7.1 主流程

```text
1. 用户选择企业与产品
   ↓
2. 上传图片、参数、报价和能力信息
   ↓
3. AI 解析产品，用户确认或修正产品画像
   ↓
4. 用户选择国家、平台、品类、时间和价格带
   ↓
5. 导入或选用已有的合规市场数据集
   ↓
6. 系统进行数据质量检查，输出可用样本范围
   ↓
7. 系统筛选相似竞品，用户可排除错误竞品
   ↓
8. AI 抽取评论中的需求、情感、人群、场景和证据
   ↓
9. 程序计算需求重要度、价格分布和竞争指标
   ↓
10. 系统将需求转化为产品/工艺要求
   ↓
11. 与企业制造能力和成本约束匹配
   ↓
12. 生成机会分项、置信度、风险和待验证项
   ↓
13. 生成产品机会报告
   ↓
14. 人工标记：进入评审 / 打样 / 暂缓 / 驳回
```

## 7.2 业务状态流转

```text
草稿
 → 待确认产品画像
 → 待数据检查
 → 分析中
 → 待人工复核
 → 已发布
 → 已进入打样 / 已暂缓 / 已驳回
```

异常状态：

- 数据不足；
- 数据格式错误；
- 产品参数冲突；
- 模型调用失败；
- 分析部分完成；
- 用户取消。

## 7.3 人机协同控制点

| 控制点 | 必须人工确认的原因 |
|---|---|
| 产品画像确认 | 图片无法可靠识别海绵密度、内部框架等隐藏属性 |
| 竞品集合确认 | 向量相似不等于商业上真正可比 |
| 工艺可行性复核 | AI 无法仅凭通用知识确认工厂实际设备和产线限制 |
| 成本影响复核 | 没有 BOM 和供应商报价时，成本只能作为待验证假设 |
| 打样/备货决策 | 属于高成本、有外部影响的企业决策，不允许系统自动执行 |

# 8. 功能需求

## 8.1 FR-01 企业能力画像

### 解决问题

通用市场工具不知道企业能做什么、什么成本能做、能否满足 MOQ 和认证要求。

### 使用用户

企业管理者、产品/研发负责人。

### 输入

- 主营品类；
- 可用材料；
- 工艺和设备能力；
- 定制项；
- 成本区间；
- MOQ 区间；
- 交付周期；
- 包装与物流能力；
- 已有认证及目标市场。

### 处理逻辑

1. 使用标准枚举和自定义字段建立企业能力画像；
2. 对金额、尺寸、周期和 MOQ 进行单位标准化；
3. 每项能力记录来源、更新时间和确认人；
4. 认证文件只记录元数据和有效期，V1 不自动判定合规。

### 输出

- 企业能力画像；
- 能力缺失清单；
- 数据完整度；
- 最后确认人和时间。

### 业务规则

- BR-01：未填写的能力字段不等于“不具备”，必须标记为“未知”。
- BR-02：超过配置有效期的成本和认证信息不得用于高置信度推荐。

### 验收标准

- 用户可新建、编辑和版本化企业能力画像；
- 系统能区分“是”、“否”和“未知”；
- 所有用于评分的能力字段可追溯到来源。

## 8.2 FR-02 产品资料上传与多模态理解

### 解决问题

产品信息分散在图片、参数表、PDF 和报价中，无法直接与市场数据匹配。

### 使用用户

产品/研发负责人、市场运营人员。

### 输入

- JPG/PNG/WebP 产品图片；
- XLSX/CSV 参数与报价；
- PDF 产品册；
- 用户手工输入的产品补充信息。

### 处理逻辑

1. 文件类型、大小和安全性检查；
2. 文本、表格和图片信息抽取；
3. 使用视觉模型识别品类、风格、颜色、可见材质、功能和场景；
4. 将所有字段映射到沙发产品 Schema；
5. 进行单位归一、冲突检测和缺失项检查；
6. 要求用户确认关键字段后才允许发起分析。

### 信息优先级

```text
已确认结构化参数
> 用户明确输入
> 企业 PDF/产品资料
> 图片可见信息
> 模型推断
```

### 输出

- 标准化产品画像；
- 每个字段的值、来源、置信度和确认状态；
- 属性冲突和缺失项清单。

### 业务规则

- BR-03：模型不得仅根据图片确认真皮、海绵密度、框架材料和承重等隐藏属性。
- BR-04：“无法判断”必须作为合法输出，不得用模型常识自动补齐。
- BR-05：出厂价、成本和 MOQ 按敏感字段处理。

### 验收标准

- 支持至少 1 张产品图和 1 份参数文件组合上传；
- 关键字段冲突时不得静默覆盖；
- 用户可在一个页面中修正并确认产品画像；
- 所有 AI 输出通过 JSON Schema 校验。

## 8.3 FR-03 市场数据集导入与质量检查

### 解决问题

企业市场数据是否存在、是否可用尚不确定；没有可观测数据范围就无法产生可信结论。

### 使用用户

市场运营人员、系统管理员。

### 输入

- CSV/JSON/XLSX 竞品数据；
- CSV/JSON/XLSX 评论数据；
- 数据来源、授权方式、市场、平台、品类和时间范围。

### 处理逻辑

1. 字段映射和格式验证；
2. 商品、评论去重；
3. 缺失值、异常价格、时间范围和语言检测；
4. 评论与商品关联完整性检查；
5. 输出数据质量报告和可分析范围。

### 输出

- 数据集版本；
- 商品数、评论数、时间范围和语言分布；
- 完整度、重复率、无效率和可用样本数；
- 数据限制和警告。

### 业务规则

- BR-06：每份数据集必须有来源与使用权限记录。
- BR-07：数据量低于配置阈值时可生成探索性报告，但不得标注为高置信度。
- BR-08：销量、搜索量等不可直接获得时，必须显示为“代理指标”，不得伪装为真实销量。

### 验收标准

- 错误字段、无商品关联评论和异常价格可被识别；
- 用户可预览清洗前后样本变化；
- 所有报告固定关联数据集版本。

## 8.4 FR-04 竞品识别与可比性复核

### 解决问题

品类相同不等于商业上可比；错误竞品会污染评论、价格带和需求缺口结论。

### 使用用户

市场运营人员、产品经理。

### 输入

企业产品画像、市场数据集、目标价格带和使用场景。

### 处理逻辑

1. 先通过品类、市场、价格和关键属性进行硬过滤；
2. 使用向量相似度生成候选集；
3. 使用 rerank 模型根据品类、功能、风格、价格、材质和场景重排序；
4. 分为直接竞品、标杆竞品和替代竞品；
5. 允许用户排除、纳入或调整竞品类型。

### 输出

- 竞品清单和类型；
- 分项相似度；
- 纳入和排除理由；
- 最终分析样本量。

### 验收标准

- 用户可查看每个竞品的匹配原因；
- 用户修改竞品集合后，分析任务使用新版本且保留操作记录；
- 直接竞品与替代竞品的评论不默认混合统计。

## 8.5 FR-05 家具评论需求挖掘

### 解决问题

人工每天查看评论只能获得零散印象，无法稳定识别跨商品、跨时间的需求模式。

### 使用用户

市场运营人员、产品经理。

### 输入

经清洗的评论文本、评分、时间、商品、市场、语言和可选验证购买标记。

### 家具需求本体

一级类别至少包括：舒适性、尺寸与空间、材质与触感、结构稳定性、耐用性、安装难度、清洁维护、功能设计、外观审美、包装运输、气味与环保、性价比和售后服务。

### 处理逻辑

1. 语言检测、去重、垃圾文本过滤和短文本标记；
2. 将一条评论拆分为多个观点；
3. 对每个观点抽取需求标签、极性、严重程度、人群、场景、对应产品属性和原文证据；
4. 对相似观点进行向量聚类；
5. 由模型提议聚类名称，并映射到行业本体；
6. 程序计算提及频率、跨商品覆盖率、时间分布和评分分布。

### 输出

- 正向购买动机；
- 负向用户痛点；
- 中性使用场景和偏好；
- 人群和场景分布；
- 每个洞察的样本量、比例、原始证据和置信度。

### 业务规则

- BR-09：一条评论可包含多个情感相反的观点，不得仅输出单一评论情感。
- BR-10：报告展示的比例必须明确分母，如“有效评论”、“负面观点”或“覆盖商品”。
- BR-11：原文证据与翻译文同时保留；翻译不覆盖原文。

### 验收标准

- 用户可按标签、情感、人群、场景、星级和时间筛选；
- 点击任一洞察可查看对应原始评论；
- 不支持证据的模型总结不得进入最终报告。

## 8.6 FR-06 市场、价格与竞争洞察

### 解决问题

单看评论无法判断需求是否具有足够市场价值，也无法判断价格空间和竞争门槛。

### 使用用户

市场运营、产品经理、企业管理者。

### 输入

竞品价格、促销、评分、评论数、上架时间、可用的排名/销量代理指标和评论洞察。

### 处理逻辑

- 按价格段统计商品数、评分、评论数和功能卖点；
- 计算品牌集中、价格离散、功能同质化和问题解决覆盖率；
- 当有足够时间序列数据时，计算评论、新品和需求提及的变化；
- 没有时间序列数据时，隐藏“趋势”结论，只展示当期快照。

### 输出

- 价格带分布；
- 主流卖点和渗透率；
- 竞争强度分项；
- 需求与竞品解决方案矩阵；
- 有数据依据时的时间趋势。

### 验收标准

- 价格统计明确币种、含税/促销口径和数据时间；
- 趋势图必须基于至少两个时间点，不允许从单时点推断增长；
- 用户可从每个指标下钻到商品或评论样本。

## 8.7 FR-07 需求缺口与产品工程化转换

### 解决问题

“座垫不舒服”等消费者表达无法直接指导工厂改产品。

### 使用用户

产品经理、研发负责人。

### 输入

需求聚类、原始证据、受影响人群/场景、当前产品参数、家具行业知识库。

### 处理逻辑

1. 区分“用户表达”、“产品问题假设”和“工程动作建议”；
2. 检索与问题相关的属性、材料和工艺知识；
3. 生成一个或多个可能根因，不强行单一归因；
4. 生成产品参数、材料、结构、包装或说明书层面的备选动作；
5. 为每个动作生成风险、所需补充信息和验证方法。

### 输出

```text
用户问题：座垫使用一段时间后下陷
证据：涉及 N 条观点、M 个商品、时间范围 T
可能根因：海绵密度/回弹、层结构、支撑结构
备选动作：调整材料或结构，具体参数待工程复核
影响：成本/重量/包装/舒适度可能变化
验证：小样测试、耐久测试、用户体验对比
```

### 业务规则

- BR-12：没有企业 BOM 或供应商报价时，不得生成精确成本增量。
- BR-13：没有工程规范依据时，不得生成确定性材料或尺寸参数。
- BR-14：工程建议默认状态为“待专家复核”。

### 验收标准

- 每项建议包含问题、证据、根因假设、备选动作、风险和验证方法；
- 用户可将建议标记为可行、待确认或不可行；
- 系统保留人工修订前后版本。

## 8.8 FR-08 企业适配与产品机会评分

### 解决问题

单一市场热度无法回答企业是否值得投入。

### 使用用户

企业管理者、产品经理。

### 输入

需求热度、需求增长、未满足程度、竞争空间、利润假设、企业能力画像和数据质量。

### 评分结构

```text
机会基础分 =
20% × 需求热度
+ 15% × 需求增长
+ 20% × 未满足程度
+ 15% × 竞争空间
+ 10% × 利润空间
+ 20% × 企业适配度
```

权重为 V1 业务假设，必须支持版本化，并通过客户专家反馈校准。

### 置信度与总分分离

- 机会分表示样本数据中的相对吸引力；
- 置信度表示数据是否足以支撑该结论；
- 不得将高机会分、低置信度包装为“强推荐”。

### 输出

- 总分和六项分数；
- 数据置信度；
- 企业适配项和缺口项；
- 权重版本和计算依据；
- 建议结论：优先验证、补数据后再评估、工厂能力不匹配或机会有限。

### 验收标准

- 分数可重算且同一输入在同一算法版本下结果一致；
- 用户可查看每个子分数来自哪些底层指标；
- “未知”字段不得按零分处理，而应降低置信度或使用不包含该项的分数口径。

## 8.9 FR-09 产品机会报告与证据溯源

### 解决问题

企业需要可支持决策的报告，而不是一段无法验证的 AI 长文。

### 使用用户

所有业务角色。

### 报告内容

1. 分析范围和数据质量；
2. 产品画像；
3. 竞品集合；
4. 目标人群和使用场景；
5. 购买动机和高频痛点；
6. 价格带和竞争格局；
7. 需求缺口；
8. 企业适配与能力缺口；
9. 产品机会分项和置信度；
10. 产品改进假设；
11. 风险和待验证项；
12. 决策建议和人工状态。

### 交互要求

- 任一关键结论都有“为什么”入口；
- 点击后展示统计口径、商品样本、原始评论、引用时间和算法版本；
- 报告显示“事实”、“推断”、“建议”和“待验证”标记；
- 用户可填写评审结论和原因。

### 输出

Web 报告；后续版本支持 PDF 导出。

### 验收标准

- 高优先级建议 100% 包含证据入口；
- 原始数据不得在报告生成时被大模型改写；
- 企业敏感成本字段按角色权限隐藏。

## 8.10 FR-10 分析任务、版本与反馈闭环

### 解决问题

市场数据、产品参数和评分权重会变化，如果不记录版本，报告无法复现也无法学习。

### 功能要求

- 记录产品版本、数据集版本、本体版本、Prompt 版本、模型版本和评分版本；
- 任务失败时保留已完成阶段，支持从失败节点重试；
- 用户可标记建议是否正确、可行和已采用；
- 后续记录打样结果、上市表现和人工备注。

### 验收标准

- 任一报告可复现到当时使用的输入与版本；
- 模型或数据失败时不会生成伪完整报告；
- 人工反馈不覆盖原始 AI 输出。

# 9. 数据需求与数据模型

## 9.1 核心实体

| 实体 | 主要内容 | 关键关系 |
|---|---|---|
| Enterprise | 企业与租户信息 | 拥有产品、能力和用户 |
| CapabilityProfile | 材料、工艺、成本、MOQ、认证等 | 用于企业适配评分 |
| Product | 产品基础信息与当前版本 | 关联产品画像和资产 |
| ProductProfile | 结构化属性、来源和置信度 | 用于竞品匹配 |
| MarketDataset | 市场、平台、时间、来源和质量 | 固定分析样本范围 |
| Listing | 竞品商品、价格、卖点和表现 | 关联评论 |
| Review | 原始评论、语言、评分和时间 | 被拆分为观点 |
| ReviewAspect | 需求、情感、人群、场景和证据 | 关联本体标签 |
| Opportunity | 需求缺口与指标 | 关联企业适配和报告 |
| Recommendation | 问题、根因假设、动作、风险和验证 | 必须关联证据 |
| AnalysisJob | 任务状态和全部版本 | 产生报告 |
| Report | 面向用户的决策输出 | 关联任务和人工反馈 |

## 9.2 数据分级

| 级别 | 示例 | 处理要求 |
|---|---|---|
| 公开数据 | 经合规渠道取得的公开商品信息 | 记录来源、时间和使用条件 |
| 企业内部数据 | 产品参数、产品册 | 租户隔离、权限控制 |
| 企业敏感数据 | 成本、报价、MOQ、订单 | 字段级权限、加密、日志脱敏 |
| 客户/个人数据 | 邮件、联系人、客户反馈 | V1 不接入；后续需最小化、脱敏和授权 |

## 9.3 数据保留

- 原始上传文件、中间结果和报告分开设置保留周期；
- 用户可删除分析任务及关联文件；
- 删除操作进入审计日志，不在普通界面显示已删除商业内容；
- Demo 数据必须脱敏，不得展示客户真实供应商、采购商联系信息和未授权成本。

# 10. AI 与算法规格

## 10.1 AI 任务分工

| 任务 | 处理方式 | 原因 |
|---|---|---|
| 图片中的品类、风格和可见功能 | 视觉语言模型 | 需要多模态理解 |
| PDF/参数文本结构化 | 文本模型 + Schema 校验 | 输入格式多样 |
| 评论观点抽取 | 轻量文本模型 | 批量、结构化任务 |
| 语义聚类 | Embedding + 聚类算法 | 需要一致和可重复 |
| 竞品及证据重排 | Rerank 模型 | 提高相关性 |
| 价格、比例、趋势和分数 | 确定性程序 | 不允许大模型编造数值 |
| 工程化建议 | RAG + 推理模型 + 人工复核 | 需要行业知识且风险较高 |
| 报告自然语言表达 | 文本生成模型 | 输入已是结构化事实 |

## 10.2 模型选型

根据赛事提供的 Model Router 能力，V1 候选配置为：

| 场景 | 候选模型 | 调用策略 |
|---|---|---|
| 产品图片理解 | qwen3-vl-plus / qwen3-vl-flash | Demo 优先 plus，批处理可使用 flash |
| 评论抽取 | qwen3.5-flash 或赛事实际可用的轻量模型 | 分批、结构化输出、失败重试 |
| 复杂推理 | qwen3.7-max / deepseek-r1 | 仅用于聚合后的高价值节点 |
| 报告生成 | qwen3.6-plus | 只接收已验证的结构化事实 |
| 向量化 | text-embedding-v4 | 观点聚类和产品匹配 |
| 重排序 | qwen3-rerank | 竞品和证据重排 |

> 模型名称以赛事实际分配账号中可调用的模型为准。系统必须通过配置切换模型，不将具体模型 ID 硬编码到业务逻辑。

## 10.3 RAG 与行业知识库

知识库包含：

- 沙发品类、结构、功能和属性术语；
- 常见材料、工艺及其影响；
- 尺寸、舒适性、耐用性、包装和安装问题；
- 企业产品参数和已确认能力；
- 经专家复核的历史问题—动作映射。

检索必须先按企业、品类、市场和版本进行元数据过滤，再执行向量召回和 rerank。

## 10.4 幻觉控制

- 数值不交给生成模型计算；
- 模型输出必须通过 JSON Schema 验证；
- 关键结论必须关联 evidence_id；
- 证据不足时输出 `insufficient_evidence`；
- 区分 observation、inference、recommendation 和 validation_required；
- 对高风险工程建议要求人工确认；
- 通过固定测试集回归评估 Prompt 和模型变更。

## 10.5 置信度

置信度至少考虑：

- 有效评论数；
- 覆盖商品数；
- 时间覆盖；
- 跨商品一致性；
- 数据源完整度；
- 抽取模型的评估表现；
- 企业能力信息完整度。

置信度不使用大模型主观打分，而由明确规则计算。

# 12. 非功能需求

## 12.1 性能需求

| ID | 需求 | MVP 目标 |
|---|---|---|
| NFR-P01 | 普通页面加载 | P95 ≤2秒，不含大文件上传 |
| NFR-P02 | 产品画像首次结果 | 单产品目标≤60秒 |
| NFR-P03 | 评论处理 | 1,000 条评论完整链路目标≤5分钟 |
| NFR-P04 | 进度可见性 | 异步任务每≤2秒更新状态 |
| NFR-P05 | 证据下钻 | 已缓存数据 P95 ≤1秒 |

## 12.2 容量需求

MVP 设计容量：

- 单企业至少 100 个产品画像；
- 单数据集至少 100 个竞品、10,000 条评论；
- Demo 默认用于 1 个企业、1 个品类和 1 个主市场；
- 同时运行 3 个分析任务时不得破坏任务状态一致性。

## 12.3 可用性与可恢复性

- 分析工作流必须支持节点级重试；
- 幂等任务不得重复计费或重复写入报告；
- 单个模型调用失败不删除已完成的中间结果；
- 固定演示数据应预计算部分结果，但界面需清晰说明演示模式；
- 复赛演示前必须准备录屏兜底，但主演示优先使用真实可运行产品。

## 12.4 安全与隐私

- 所有数据按 tenant_id 隔离；
- 使用 RBAC 限制敏感报价和成本数据；
- 对象存储使用短效签名 URL；
- API Key 只存储在服务端密钥管理中；
- 日志不记录原始报价、订单、邮件或完整 Prompt 中的敏感数据；
- 私有数据默认不用于公共模型训练；
- 上传文件进行扩展名、MIME、大小和恶意内容检查；
- 敏感操作记录审计日志。

## 12.5 可观测性

必须记录：

- 任务各阶段耗时和成功/失败状态；
- 模型名称、版本、输入/输出 token 数和重试次数；
- 向量和 rerank 调用量；
- 缓存命中率；
- 数据清洗前后样本数；
- Schema 验证失败率；
- 单任务估算成本；
- 无证据结论拦截次数。

## 12.6 可用性与无障碍

- 主流程不超过 5 个用户必需步骤；
- 所有 AI 分析状态用明确文字说明，不只显示动画；
- 图表同时提供数值和文本摘要；
- 不仅依赖颜色表示机会高低和任务状态；
- 错误信息要说明用户下一步可采取的动作。

# 13. 算力与成本需求

## 13.1 算力使用原则

1. 批量评论抽取使用轻量模型；
2. 仅对聚类结果和最终建议使用高性能推理模型；
3. 同一评论、商品和文件在内容未变更时复用缓存；
4. 向量按内容哈希去重；
5. 任务超过配额时给出估算并要求用户确认；
6. Demo 使用固定数据集和可复用中间结果，避免在现场重复消耗全量算力。

## 13.2 MVP 单任务算力拆分

| 环节 | 单次规模假设 | 调用类型 | 成本控制 |
|---|---:|---|---|
| 产品图片理解 | 1—5 张图 | 视觉语言模型 | 图片去重、限制分辨率、缓存 |
| 文件结构化 | 1 份参数表 + 可选 PDF | 轻量文本模型 | 先本地解析，只将难以映射内容送模型 |
| 评论观点抽取 | 1,000 条评论 | 轻量文本模型 | 分批、结构化输出、并发上限 |
| 语义向量 | 清洗后观点 | Embedding | 哈希去重、增量计算 |
| 竞品/证据重排 | 候选 Top-K | Rerank | 先硬过滤缩小 K |
| 聚类命名 | 约 10—30 个聚类 | 文本模型 | 只处理聚合摘要 |
| 工程建议 | Top 3—5 需求缺口 | 高性能推理模型 | 限制高价值节点 |
| 报告生成 | 1 份 | 中/高性能文本模型 | 仅输入结构化结果 |

## 13.3 算力估算方法

由于赛事额度、模型价格和具体评论长度尚未完全确定，V1 不伪造精确金额。开发时通过以下公式估算：

```text
单任务模型成本 =
Σ（输入 Token × 模型输入单价
+ 输出 Token × 模型输出单价
+ 图片/向量/Rerank 调用成本）

阶段算力预算 =
单任务成本 × 预计任务数 × 安全系数
```

安全系数用于覆盖调试、重试和模型对比，建议初期按 1.5—2.0 配置。

## 13.4 基础资源建议

MVP 非模型服务可从小规格起步：

- Web/API：2—4 vCPU、4—8 GB 内存；
- Worker：4 vCPU、8 GB 内存，按并发任务扩展；
- PostgreSQL/pgvector：2—4 vCPU、4—8 GB 内存；
- Redis：1—2 GB 内存；
- OSS：按上传文件和中间产物实际用量配置。

以上为 Demo 级别初始值，需在批处理压测后调整，不代表商用容量。

### 测试集

# 16. 落地约束与风险管理

## 16.1 核心约束

| 约束 | 影响 | 处理方案 |
|---|---|---|
| 市场数据尚未确认 | 可能无法计算趋势和真实销量 | 尽快完成数据盘点；MVP 支持合规文件导入 |
| 问卷部分内容由 AI 生成 | 业务事实可能失真 | 对关键决策进行二次访谈确认 |
| 复赛开发时间短 | 无法覆盖全品类和实时全网数据 | 收缩为沙发 + 单市场 + 固定数据集 |
| 模型可用性和额度受赛事平台限制 | 可能超时或额度不足 | 模型路由、缓存、轻量模型和预计算兜底 |
| 家具工程知识不足 | 建议可能不可制造 | 工程人员复核；建议标记为假设而非指令 |
| 销量和搜索数据可能不可得 | 需求热度只能使用代理指标 | 明确口径，降低置信度，不冒充真实销量 |

## 16.2 风险清单

| ID | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|:---:|:---:|---|
| RK-01 | 项目被评为 Amazon 现有工具的重复 | 高 | 高 | 聚焦制造企业私有能力、工程化转换和证据链 |
| RK-02 | 数据无法合规获得 | 中高 | 高 | 先确认客户导出数据和授权数据源；演示使用脱敏数据集 |
| RK-03 | 评论样本不代表整个市场 | 高 | 中高 | 显示平台、品类、时间和样本限制，不过度外推 |
| RK-04 | AI 建议过于确定 | 中 | 高 | 事实/推断/建议分层，工程复核和证据门禁 |
| RK-05 | 机会评分权重缺乏依据 | 高 | 中 | 标记为 V1 假设，版本化并用专家排序数据校准 |
| RK-06 | Demo 现场模型超时 | 中 | 高 | 异步进度、重试、备选模型、缓存和录屏兜底 |
| RK-07 | 范围膨胀为全链路 Agent | 高 | 高 | 严格使用 P0/P1/P2 边界，任何新功能必须替换而非追加 P0 |
| RK-08 | 客户实际核心问题仍是 B2B 找客户 | 中 | 中高 | 二次访谈；本项目讲清“先确定什么值得卖”的赛题边界 |

# 18. 商业化与业务闭环

## 18.1 商业闭环

```text
市场数据 + 企业产品/能力
            ↓
产品机会与改造假设
            ↓
人工评审与打样
            ↓
客户/市场验证
            ↓
上市表现与人工反馈
            ↓
校准标签、映射和机会排序
```

没有最后三步，产品只是一个一次性报告工具；建立反馈后，才有可能形成垂直数据壁垒。

## 18.2 付费价值假设

企业可能为以下价值付费：

- 缩短人工市场分析时间；
- 提高评论和竞品分析覆盖率；
- 减少不匹配新品进入打样的概率；
- 复用企业内部产品和能力数据；
- 形成可用于内部产品会的证据化报告。

付费模式需通过试点验证，候选包括：按帐号订阅、按分析任务付费、企业私有化部署和数据/品类知识库定制。V1 不设定未验证价格。

## 18.3 业务效果计算

试点阶段记录：

```text
单次分析节省工时 =
人工原耗时 - 使用 FurniScope 的人机协同耗时

建议转化率 =
进入人工评审的建议数 / 总建议数

打样采用率 =
进入打样的建议数 / 进入人工评审的建议数
```

“降低新品失败率”只能在积累足够产品周期数据后评估，不作为黑客松当期可证明指标。

# 19. 赛事评审适配性

## 19.1 业务价值

- 需求来自真实家具出口企业调研；
- 解决的是新品立项前的高价值决策，不是低价值内容生成；
- 产品输出可进入产品评审和打样讨论。

## 19.2 创新性

- 家具垂直需求和工艺本体；
- 从用户表达到工程动作的转换；
- 市场机会与企业制造能力联合评估；
- 决策证据链和人机协同。

## 19.3 落地可行性

- 收缩为沙发、单市场和固定数据集；
- 使用成熟的视觉理解、文本抽取、Embedding 和 Rerank 能力；
- 数值计算与大模型生成分离；
- 客户已具备产品图片、参数和报价等基础数据。

## 19.4 技术完整性

- 定义了输入、数据质量、AI 抽取、确定性计算、RAG、报告和证据回溯全链路；
- 包含模型分工、算力控制、失败兜底、性能目标和评测方法；
- 对数据合规、幻觉、样本偏差和工程风险有明确约束。

## 19.5 答辩核心口径

### 为什么不直接用 Amazon Product Opportunity Explorer？

Amazon 工具擅长利用平台内搜索、购买、评论和价格数据发现市场机会。FurniScope 不与它比拼 Amazon 数据规模，而是解决制造企业的后半段问题：这个机会是否适合某家工厂，应转化为哪些尺寸、材料、结构和包装动作，以及证据和风险是什么。

### 为什么 AI 不是技术堆砌？

每类模型只承担它擅长的任务：视觉模型理解图片，文本模型抽取评论观点，Embedding 聚类，Rerank 筛选证据，推理模型在行业知识和证据约束下生成建议。价格、比例和机会分仍由程序计算。

### 如何证明有用？

不以“报告生成成功”作为业务成功，而是使用客户专家盲评、建议进入产品评审的比例、人工分析工时变化和后续打样反馈验证。

# 附录 B：关键术语

| 术语 | 定义 |
|---|---|
| 产品画像 | 从图片、参数和资料形成的标准化产品属性集 |
| 需求观点 | 一条评论中针对某个产品属性的独立表达 |
| 需求缺口 | 用户关注度高、满意度低且现有解决方案不充分的需求 |
| 企业适配度 | 市场机会与工厂品类、材料、工艺、成本、MOQ、认证和交付能力的匹配程度 |
| 机会分 | 基于当前数据和规则计算的相对吸引力，不等于销售成功概率 |
| 置信度 | 当前数据覆盖和模型质量对结论的支撑程度 |
| 证据链 | 从决策建议回溯到指标、商品、评论和企业参数的关联 |
| 销量代理指标 | 在真实销量不可得时用于反映商品表现的间接信号，必须明确标注 |
