# FurniScope 后续增量开发提示词 V2

## 1. 文档用途

本文档用于从 FurniScope 当前真实代码断点继续开发。每次只复制“总控提示词”和一个对应迭代提示词交给编码 Agent，不要一次执行全部迭代。

当前产品定位为“跨境家具超级 AI 员工”，系统角色只有 `user` 和 `admin`。前端技术栈已正式调整为 **React 19 + Vite**，不再使用 Svelte。

## 2. 当前系统已经开发到什么程度

### 2.1 已完成并应直接复用

| 模块 | 当前状态 | 主要实现位置 |

## 3. 推荐开发顺序

```text
分析任务 API
  → user_confirmation API 与恢复 Worker 接入
  → 洞察/报告只读 API
  → 工作台汇总 API
  → React API 基础层与认证
  → React 新建分析和执行中页面
  → React 洞察与报告页面
  → Admin P1
  → 全链路验收与生产化
```

不要先把全部静态页面接一遍再补后端。应先完成一条真实纵向链路：

```text
登录 → 产品/数据集 → 创建任务 → 启动 Agent → 查询五阶段进度
→ 必要时确认 → 恢复执行 → 查看洞察 → 查看决策报告
```

## 6. 迭代 3E｜user_confirmation 与安全恢复

```text
基于总控提示词和已完成的分析任务 API，本轮只实现统一确认事项 API 与恢复 Worker 的 FastAPI 接入。

必须实现：
1. API-CFM-01 GET /api/v1/user-confirmations；
2. API-CFM-02 POST /api/v1/user-confirmations/{confirmation_id}:respond。

实现要求：
1. API 投影严格使用数据字典规定的 user_confirmation 九字段；
2. confirmation_id、confirmation_type、question、recommended_option、options、evidence_refs、impact、checkpoint_stage、expires_at 由服务端已有状态提供；
3. 客户端不得提交 tenant_id、task_uuid 或 checkpoint_stage 覆盖服务端状态；
4. 回答接口接入 Idempotency-Key；
5. 复用现有 Repository 原子事务：锁定确认记录、校验租户/用户/状态/期限/选项、写回答、写 workflow_control_events 和 Outbox；

8. 只允许 safe Checkpoint；Checkpoint 冲突必须返回文档规定错误；
9. 同答案重复提交返回原结果，不同答案重复提交冲突；
10. Worker 租约到期可重领，重复消息不能造成重复模型调用；
11. API-INS-03 能同步显示当前 confirmation、checkpoint_stage 和恢复后的阶段状态。

必须测试：生成、列表过滤、跨租户、回答、幂等、异答案冲突、过期、非法选项、非 safe Checkpoint、事务回滚、Outbox 重复消费、租约重领、Worker 重启和最终恢复完成。

交付准入：回答受理与 Agent 恢复必须通过真实 PostgreSQL 事务测试，且失败时不出现“确认已回答但无恢复事件”的半完成状态。
```
