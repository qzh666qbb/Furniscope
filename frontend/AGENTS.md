# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

This is the unified FurniScope product prototype. Keep the seven selected experiences connected in one app: login, AI workspace, new-analysis wizard, execution dashboard, market insights, decision report, and admin control center. The only supported roles are user and admin; do not add a role selector or RBAC matrix.

The primary product sidebar is collapsible. Preserve icon-only navigation, active states, tooltips, route behavior, and the user's saved collapsed/expanded preference.

The primary sidebar has no separate collapse arrow. Clicking the FurniScope brand mark toggles the sidebar between expanded and icon-only modes; keep that mark usable in both states with an accessible label and tooltip.

The current app is the only maintained UI. Treat the archived old UI as a business-pattern reference: reuse product-data validation, data-quality checks, competitor/review evidence drill-down, engineering validation, and admin diagnostics without restoring its dense top-level navigation, persona-specific entrances, or user-facing internal agent graph.

SKU demand forecasting belongs inside Market Insights rather than primary navigation. Present it as demand forecasting and production planning: forecast scope, period, scenario, model quality, market-preference signals, recommended production volume, safety stock, and scheduling; carry the result into the decision report's manufacturing section.

The standalone product sales forecast workspace keeps three tenant-user tabs: “销量预测”, “历史预测记录”, and “模型训练”. Enterprise users may append their own tenant-scoped order and inventory workbooks and trigger automatic retraining directly; this flow does not require administrator login or approval. The forecast form includes day, week, and advanced-business modes, multi-site selection, optional start date, and price/discount/inventory/promotion/cold-start inputs. Do not expose internal model version identifiers in this user-facing workspace; show model readiness and the current data-through date in the page summary card, and refresh both status and SKU coverage after a successful data update. Do not embed a recent-forecast card or record count in the forecast form. The dedicated history tab is API-backed, searchable and filterable, shows 10 records per page, opens completed results in a modal, and supports CSV and JSON result exports.

The primary analysis experience is conversational. Keep the conversation, uploaded files, concise inspectable execution summaries, and follow-up composer available throughout the task. The right side is a collapsible dual-mode panel: execution context while work is running, and analytical results after output is available, with users able to switch between both modes at any time. Never expose private chain-of-thought or internal agent controls.

Keep both analysis modes. The workspace lets users choose conversational analysis or the structured wizard. In conversational mode, organize history as analysis project (product/market objective) -> project conversation -> conversation results; expose that hierarchy in a collapsible secondary sidebar without replacing the primary product navigation.

The analysis history sidebar has two explicit organization modes: ordinary unfiled conversations and project archives. Users must be able to search, open, fold, create project categories, archive an ordinary conversation into a project, and move an archived conversation back to ordinary history.

Market Insights and Decision Reports are asset collections, not single pages. Primary navigation opens searchable list views; users then open a selected insight/report detail. Decision reports expose download actions from both the list and detail views.

Market Insights is also the authoritative market-dataset management surface. It must provide real CSV/JSON/XLSX import, automatic review cleaning and before/after statistics, reusable tenant-scoped datasets, competitor/review source previews, replacement uploads, soft deletion, and links back to consuming analysis tasks. The dataset list is a compact paginated table (10 rows per page), not a stack of full-width cards. The import-dataset modal follows the product-center modal anatomy: dimmed backdrop, eyebrow/header/close, scrollable form, sticky footer with teal primary action. The monitoring workspace top switcher (竞品分析 / 评论舆情) and the competitor sub-tabs (价格趋势 / 版本对比 / 上新与促销) are equal-width full-row controls with no unused right gutter. Do not surface 主动采集, 政策预警/外部通知, or 变更告警 in the product UI. Dataset detail shows listings/reviews preview only; do not show authorization-provenance or bound-analysis-task cards. Market Insights summary cards count real `market_listings` / `reviews` rows, not denormalized placeholders on empty demo archives. 评论舆情 reads valid dataset reviews as the primary corpus (paginated, with server-side positive/negative/neutral totals) and treats URL 获取舆情 as an incremental ingest into a selected dataset plus the live event stream. JSON ingest is not a user-facing step. Filter controls in 舆情事件 stay on one row. Change-alert “标为已读” sits on the right of each list row and uses the same teal outline button style as the rest of the system.

The AI workspace landing page uses the operations-dashboard hierarchy established in September 2026: four KPI cards with concise status subtitles, the existing five-stage task list, a four-card outcome snapshot, and a sticky recent-reports rail. Do not show a simulated “AI 实时分析动态” feed or imply continuous live analysis from hardcoded events. Keep task/data refresh connected to real APIs, and keep success/running/warning states visually distinct only where backed by actual task state.

The homepage “AI 工作流任务” rows keep product identity and the five-stage tracker in separate columns. Product titles wrap at most two lines and never overflow onto stage labels; SKU is shown once as a compact badge rather than concatenated onto the title. Every outcome card is an accessible drill-down into that same task's corresponding market-insight tab, and its labels must describe the actual persisted metric rather than overclaiming “blue-ocean” or high-priority findings.

Primary navigation calls the operations landing page “首页” and the single analysis experience “AI 工作台”; do not restore a second “分析中心”. The AI Workbench is a Dify-style node canvas with a top-to-bottom automated chain, inspectable node-detail rail, and collapsible grounded chat. Homepage task creation/history and Product Center “开始分析” both enter this same canvas, with product data auto-filled for Product Center launches.

Keep system “首页”, “AI 工作台” home, and the analysis canvas as three distinct levels. User-facing copy calls the canvas “分析工作台”, never “Plane 工作台”. The AI Workbench navigation route first opens its own landing page; its entry action opens the named-workspace/history modal, while Product Center may bypass that modal and enter the analysis workspace directly with the product prefilled. Never place the workspace creation modal on the system operations homepage.

Analysis-workspace history is workspace-scoped, not run-scoped: render one list row per workspace and allow multiple analysis tasks/runs inside it. Starting another analysis in the same workspace must update that row's latest state and analysis count instead of creating another workspace record. The AI Workbench home card is titled “工作日记” and shows the latest 10 workspaces; the top-right “更多” opens a full list with search, status filter, pagination, view, and delete. Deleting a work-diary row archives its analysis tasks and decision reports together. Archiving a decision report likewise cancels the related analysis task so it disappears from homepage “AI 工作流任务” and 工作日记.

Report detail back-navigation is source-aware: reports opened from AI Workbench or Plane return to the AI Workbench home; reports opened from the Decision Reports collection return to that collection. Preserve the source context for PDF/print entry points as well.

Every child view opened from a primary-navigation destination must show a consistent, visible parent-page tab near the top of the child content. The tab must name and return to the actual source page (including source-aware paths such as Home, Product Center, AI Workbench, Market Insights, dataset detail, Decision Reports, or report detail), and drawers or inline result views must provide the same explicit way back to their parent state.

Do not restore a user-facing enterprise manufacturing-capability settings page or a “制造匹配” insight tab. Opportunity scoring is market-only (demand heat, growth, unmet need, competition space, profit space). Factory-fit heuristics remain backend-internal and must not drive recommendation level or the visible radar.

Keep the AI Workbench canvas genuinely pannable and zoomable. Task progress should prefer authenticated SSE with polling fallback; completed nodes must use tenant-scoped competitor, review, cluster, opportunity, recommendation, and evidence projections rather than decorative sample results. Workflow chat may call the configured model router only with the completed task context and must retain a deterministic grounded fallback when the model service is unavailable.

The Plane workspace uses four freely resizable desktop columns inside the global product shell: task-bound conversation history, the active tool-aware AI conversation, a compact central pannable node canvas, and a right report previewer that can switch to the selected node's parameters, progress, evidence, and logs. Column gutters are draggable splitters; history, chat, and preview store pixel widths (with generous min/max), the canvas takes remaining space, and previously saved widths that were capped too tightly should be allowed to grow. Give the active AI conversation a larger default width than the old fixed canvas strip. History, current-message records, and the complete AI conversation area are collapsible but default to expanded. Opening a historical conversation restores its product, dataset, workflow state, and report context; a new conversation starts a clean analysis context. Persist user-adjusted pane widths locally, while migrating previously saved chat or history widths that are too narrow. Canvas nodes are selectable execution boundaries: users may run only through product parsing, market research, opportunity scoring, or plan generation, while full report generation remains explicit. Scoped runs include required upstream dependencies and stop without fabricating a report. Conversational intent must synchronize the selected canvas boundary (for example competitor/review requests select market research, scoring requests select opportunity evaluation, and report requests select the full workflow).

The public authentication experience includes enterprise login, an account-only “remember me” option that never persists passwords, a registration/application page, password-recovery guidance, and a clearly separated administrator portal. Keep admin authentication visually and behaviorally distinct from tenant-user login; do not add role selection to either form.

The top-right user dropdown has exactly one action: “退出登录”. Keep page navigation and enterprise settings in the primary sidebar rather than duplicating them in the user menu.

The administrator is a platform operator, while every ordinary user is an enterprise customer account. Keep the admin control center intentionally limited to two primary domains: enterprise users (tenant onboarding, status and product entitlements) and tenant forecast models (data update, training, deployment history and rollback). Do not restore data sources, SKU catalog, Prompt management, model routing, or workflow diagnostics as primary admin navigation. Each enterprise user's business data and forecast deployment are isolated by tenant, even when the UI presents the tenant and its primary login as one enterprise-user record.

Administrator lists must be database-backed and must never present mock, E2E, external-test, or approval-demo tenants as business records. Show each real enterprise login account explicitly, even when multiple accounts share one tenant; keep forecast models grouped by tenant so one HeFeng deployment appears as one model rather than one model per login.

Enterprise-account deletion is an audited, reversible soft delete. Close the tenant, disable its enterprise login accounts, revoke active sessions, and hide it from default enterprise and forecast-model lists without deleting business or audit data. Keep deleted enterprises available through the “已删除” filter for recovery, and never allow an administrator to delete the tenant that contains their current account.

In the administrator forecast-model workspace, creating an enterprise account already creates its forecast-model record, so do not expose a separate “新增模型” action. Keep “更新模型” inside that tenant's “企业私有模型空间”; it is a tenant-specific engine replacement flow that shows the current deployment by default and accepts reviewed model code plus JSON parameters for a new XGBoost, LightGBM, or custom compatible implementation.

Admin overview metrics use a cohesive four-card single-row grid with clear numeric hierarchy and restrained status accents. Keep all four cards on one row, using horizontal overflow only as a narrow-screen fallback; avoid rendering KPI labels, values, and descriptions as unstyled vertical text blocks.

The Product Center is the enterprise product-record foundation. Keep its compact filter toolbar, independent product record cards, real single-product creation and multi-asset parsing, Excel bulk creation, and inspectable product-profile drawer. Product attributes always follow `manual entry > document extraction > AI vision/inference`; surface disagreements as conflicts and let users correct them without losing unaffected profile attributes.

Product Center is the canonical user-facing SKU for forecasting. Forecast catalog rows are the current product SKUs mapped onto Sales Forecast V4 training SKUs; engine SKUs that do not map to a product are dropped. Mapped products run the normal V4 path without a cold-start baseline. Unmapped products still require an explicit baseline or reference SKU.

Product Center cards use generous image areas and show MOQ plus USD factory price. Display meaningful catalog subcategories inferred from the enterprise product name (for example armchair, power recliner, or lift chair) instead of flattening every item to “sofa”. Do not show color as a Product Center profile metric, although source color data may remain stored for other analytical uses.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.
